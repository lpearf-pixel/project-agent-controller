# Project Agent Controller v0.1D Host Service and Community Onboarding Design

- Date: 2026-07-31
- Status: approved by the user's standing authorization to use the recommended option
- Baseline: `agent/v0.1c-git-ci-observers`
- Target project: `lpearf-pixel/community-selection-miniapp`

## 1. Mission and non-goals

v0.1D turns the verified v0.1C observer into a restartable host service and onboards Community Selection Miniapp as the first real project. Success means one operator can start, inspect, stop, emergency-stop, recover, and uninstall the controller without copying secrets into Git or granting it write access to a business repository.

v0.1D remains observer-only. It does not run project commands, rerun CI, modify Git, restart business containers, create issues, invoke a model, repair code, deploy, or change payment, refund, inventory, membership, or database state.

## 2. System boundary

The controller runs natively on the host. macOS uses a LaunchAgent; Linux uses a systemd user service. Running the controller itself in Docker is excluded because Docker Desktop and Colima cannot reliably expose macOS host process identity to psutil.

Inputs are a private environment file, a private project YAML file, local Git repositories, declared PID files, a read-only Docker endpoint, and GitHub GET endpoints. Outputs are a local SQLite WAL database, bounded local logs, sanitized localhost API responses, and process exit status. The HTTP listener remains loopback-only.

## 3. Minimum closed loop

```text
host starts service
→ strict private environment is loaded
→ project sources are observed
→ events and source states are committed
→ health and incidents are queried
→ operator drains or emergency-stops
→ service restart preserves control state
→ operator explicitly recovers
```

The service manager may restart the controller after an unexpected process failure. It must not clear `EMERGENCY_STOP`, resume a drained controller, rerun CI, or restart a business process.

## 4. Components and contracts

### 4.1 Strict environment loader

`PAC_ENV_FILE` points to one absolute regular file no larger than 64 KiB. On POSIX, group or world permission bits cause fail-closed startup. Only `PAC_*`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, and lowercase proxy equivalents are accepted. Existing process environment values win. Values are parsed as dotenv data, never sourced by a shell, and are never printed.

### 4.2 Community Selection project declaration

One production example YAML declares the repository, GitHub CI, and the production `api`, `edge`, and `postgres` containers. Docker selectors use the exact Compose project/service pair from `docker-compose.production.yml`. The development-only `admin` container is not placed in the production template. Local paths remain `local://` references resolved under `PAC_LOCAL_REPOS_ROOT` or `PAC_LOCAL_SOURCES_ROOT`. PostgreSQL addresses and credentials are not duplicated in controller project YAML.

### 4.3 Service renderer

`pac service render --platform launchd|systemd --output-dir <dir>` writes deterministic service files from explicit absolute paths. It does not install or enable them. Launchd uses `RunAtLoad`, failure-only keepalive, and a 30-second throttle. Systemd uses `Restart=on-failure`, `RestartSec=30`, and a three-restart/five-minute start limit. Both pass only `PAC_ENV_FILE` and write bounded service-manager logs outside Git.

`pac service install` is intentionally deferred. v0.1D keeps installation an explicit host command described in the runbook so repository tests never mutate a real service manager.

### 4.4 Stop and recovery

Three independent controls remain available:

1. `pac controller drain` stops new controller work while preserving queries.
2. `pac controller emergency-stop` blocks all observation/provider calls and survives process restart.
3. `launchctl bootout` or `systemctl --user stop` stops the controller process itself.

Clearing Emergency Stop enters `RECOVERING`; it never silently returns to `ACTIVE`. Uninstall removes only the service registration, not the event database, project configuration, or evidence.

## 5. Security and failure behavior

- No shell evaluation of environment files.
- No literal token, absolute user path, Docker Socket, phone number, address, or PostgreSQL DSN in tracked configuration.
- GitHub remains GET-only; Docker remains GET-only; Git remains fixed-argv status-only.
- Missing Git, Docker Socket, token, repository, container, or PID becomes an observable unavailable state rather than a startup crash where the existing provider contract allows it.
- Invalid environment permissions, invalid keys, non-loopback host, ambiguous Docker selector, or unsafe service-render path fails closed.
- Service files quote values according to their native formats and never embed secret values.

## 6. Verification

The release gate runs frozen dependency sync, Ruff, strict mypy, all pytest tests, CLI smoke, temporary Git transitions, GitHub public GET-only preflight, service rendering tests, secret/path scans, and Docker Engine integration on a GitHub-hosted Ubuntu runner. A macOS runner verifies LaunchAgent rendering and CLI startup. No workflow receives a write token or executes a business repository command.

## 7. Stage gate

v0.1D can leave Draft only when:

- all local v0.1C gates pass from a clean frozen environment;
- LaunchAgent and systemd renderers are deterministic and contain restart throttles;
- environment permission and key allowlist tests pass;
- the Community Selection example validates without literal secrets or host paths;
- real Docker GET-only preflight succeeds on the public runner;
- Emergency Stop prevents provider calls in tests;
- the runbook documents install, status, logs, drain, emergency stop, recovery, stop, and uninstall.

Real activation on the user's i9 Mac remains a host operation because this workspace cannot access that machine's LaunchAgents, Docker Desktop Socket, local repository paths, or private token.
